## 一、全景图：开发九步，AI 各站一岗

先破一个误解：

> **很多人以为"用 AI 开发"就是"让 AI 写代码"。**

写代码只是九步里的一步，而且**未必是最省时间的那一步**。

| 步 | 这一步在干什么 | AI 怎么帮你 | 对应篇章 |
|---|---|---|---|
| **① 选** | 用什么技术做 | 让 AI 排序 + 说缺点 + 划边界 | 85 |
| **② 搭** | 把项目跑起来 | 五件套脚手架，30分钟见 Hello World | 90 |
| **③ 写** | 实现功能 | 函数 / 页面 / 接口 / 数据库 / 脚本 | 61-67 |
| **④ 懂** | 看懂别人的代码 | 大白话解释、框架原理、老代码考古 | 69-70、74 |
| **⑤ 调** | 出错了怎么办 | 报错八步法、逻辑错定位、性能瓶颈 | 71-75 |
| **⑥ 改** | 让代码变好 | 重构六味、提速四招 | 77-78 |
| **⑦ 测** | 确认没坏 | 单测四靶、测试用例三层 | 79、89 |
| **⑧ 审** | 上线前把关 | Review 五关、安全排查 | 80、88 |
| **⑨ 留** | 让别人看得懂 | 注释、风格、API 文档、决策记录 | 81-83、91 |

再加贯穿全程的两条线：**前后端联调（86）** 和 **团队协作（91）**。

**这张表最重要的发现：**

> **③"写"只是九分之一。最大提效在 ④懂、⑤调、⑨留 三步。**

因为写代码你本来就会（慢一点而已），但"看懂别人的代码"和"写文档"以前是时间黑洞，现在直接砍掉 80%。

**新手最容易只用 ③，老手会把九步全用上。**

## 二、一套母版：为什么最后都是"五段式"

38 篇给了你几十个提示词，但它们长得越来越像。第68篇做过一次收敛，再确认一遍——**万能五段式**：

> ### 背 → 目 → 进出 → 约 → 交

| 段 | 一句话 | 新手常犯的错 |
|---|---|---|
| **背**（背景） | 你是谁、什么项目、给谁用 | 完全不说，AI 只能按最通用的猜 |
| **目**（目标） | 这次要做的**一件事** | 一次塞三件事，三件都是半成品 |
| **进出**（输入输出） | 什么进去、什么出来 | 只描述不给样例 —— **给一个样例胜过描述十句** |
| **约**（约束） | 技术限制、规范、安全、不要做什么 | 全靠 AI 猜，然后嫌它不合规 |
| **交**（交付） | 完整文件、什么格式、怎么验证 | 拿到"其余省略"版本，复制到崩溃 |

**所有专项方法论，本质都是这个母版在不同场景下的"填空指南"：**

| 场景 | 填空重点 | 出处 |
|---|---|---|
| 写函数 | 用途 + 输入 + 输出 + 边界 | 61 |
| 生成页面 | 定位 + 内容 + 风格 + 交互 + 技术约束 | 62 |
| 写接口 | 业务对象 + 字段清单 + 动作清单 + 技术约束 | 63 |
| 设计表 | 三必备字段 + 四提问 | 64 |
| 写文档 | 址 + 入 + 出 + 错 + 例 | 83 |
| 搭脚手架 | 做 + 用 + 跑 + 备 + 库 | 90 |

**不用背这么多。记住"背目进出约交"，需要时回来查对应那篇的填空清单。**

## 三、一页铁律：38 篇的血泪总结

这些不是技巧，是**踩过坑才知道的规矩**。

**铁律一：一次只改一件事，改完必须验一次。** 全模块最重要的一条，重构（77）、优化（78）、调试（71）、风格（82）反复出现。一次改五处，出问题时你不知道是哪一处的锅。

**铁律二：给完整文件，不要片段。** 咒语原文：

> **"从第一行到最后一行完整给我，不要用'其余省略'。"**

**铁律三：AI 说"没问题"不算数。** 它默认想让你满意。反制两招：**验伪追问**（"给我一个会真出事的具体场景"）、**三档排序**（必须改 / 建议改 / 可以不改）。

**铁律四：报错贴原文，一个字别改。** 转述的"它报了个错说找不到"，AI 只能瞎猜；原文那行文件名和行号才是关键。**三连套餐：报错原文 + 系统 + 版本号。**

**铁律五：删改数据前，先 SELECT 试跑。** `DELETE` 和 `UPDATE` 没有后悔药，**把 WHERE 条件放进 SELECT 跑一遍，看会动多少条。**

**铁律六：先让它跑，再让它好。** 脚手架阶段唯一目标是看到 "Hello World"，别顺手加功能。**跑通那一秒立刻存档，这是唯一的回退点。**

**铁律七：AI 有时间差，还偏爱新技术。** 它推荐的库可能已停维护。**要建议时顺带要官网地址自己确认；提问时明说"要稳不要新"。**

**铁律八：能举出具体例子的方案，才是真想清楚了。** 让 AI 举一个具体数据的例子，**说不出来的地方就是没想清楚**。

**铁律九：注释只写"为什么"。** What 不写、How 少写、**Why 必写**。而 Why 只有你知道，**必须先由你口语回答，再让 AI 转成注释**——跳过这步就是让 AI 猜。

**铁律十：敏感信息一律不贴。** 密钥、密码、真实用户数据、未公开商业信息。**要贴就脱敏：结构保留，内容换假的。**

## 四、五张速查表合订（贴墙版）

**改代码看这张——重构六味（77）**

> **长**（函数过长）**重**（重复）**名**（命名不清）**套**（嵌套深）**魔**（魔法数字）**杂**（职责多）

**写测试看这张——测试四靶（79）+ 边界四尺（89）**

> 四靶：**正**（正常）**边**（边界）**错**（错误）**空**（空值）
> 四尺：**数**（0/-1/上限）**字**（空/超长/特殊字符）**时**（过期/跨天/并发）**态**（连点/断网/后退）

**提交前看这张——Review 五关（80）**

> **正**（正确）→ **安**（安全）→ **错**（错误处理）→ **洁**（可读）→ **快**（性能）
> 顺序就是优先级，前三关不过，后两关不用看

**联调时看这张——对不齐四元凶（86）**

> **名**（字段名大小写下划线）**型**（"0" vs 0）**层**（嵌套层级）**空**（null/""/0/不存在）

**写文档看这张——API 文档五件事（83）**

> **址**（地址方式）**入**（请求参数）**出**（返回字段）**错**（错误码）**例**（完整示例）

## 五、五个最常见的翻车姿势

**姿势一：一句话丢过去，然后嫌 AI 笨。** "帮我写个登录功能"——AI 只能按最通用的猜。**背目进出约交，哪怕只填三段，质量差一倍。**

**姿势二：一次让它干三件事。** "帮我重构一下顺便加个缓存再补上注释"——三件都是半成品。

**姿势三：不看就复制，出事了才回头读。** **看不懂的别提交**。

**姿势四：提前优化性能。** 优化三问第一问就是"**值不值**"——用户真觉得慢吗？3 秒是分水岭。**没人喊慢就别优化。**

**姿势五：文档、测试、注释拖到最后。** 第84篇五大误区之首。**拖到最后 = 永远不做。**

## 六、能力自检：你现在在哪一档？

| | **青铜：AI 当搜索用** | **白银：AI 当外包用** | **黄金：AI 当搭档用** |
|---|---|---|---|
| **提问方式** | 一句话就发过去 | 会说清背景和要求 | 五段式成肌肉记忆 |
| **用在哪几步** | 只有"写代码" | 写 + 调 + 改 | 九步全上，尤其懂/留 |
| **拿到结果后** | 直接复制运行 | 大致看一眼 | 逐段读懂 + 主动验伪 |
| **出错时** | 重新问一遍 | 贴报错让它改 | 八步法定位，只让它改那一处 |
| **规范** | 没有 | 心里有数 | 焊进提示词，自动执行 |
| **团队** | 自己用自己的 | 偶尔分享 | 共享提示词库 + 决策留痕 |

**从青铜到白银，靠的是"把话说清楚"——练五段式。**

**从白银到黄金，靠的是"不再全信它"——练验证。**

> **AI 越强，你的判断力越值钱。**
>
> 它能替你写，替你查，替你改。
> **但"这样做对不对""这个方案值不值得"——只有你能决定，也只有你要为结果负责。**

## 提示词模板盒子

### 模板一：万能母版（背目进出约交）—— 打印出来贴墙上

```
【背景】
我在做一个（什么项目），用的是（什么技术，不确定就写"你帮我推荐，要稳不要新"），
这个东西是给（谁）用的。
我的水平：（如实说，比如"完全不懂代码，需要你把每一步说到能照做"）。

【目标】
这次我只要你做一件事：（具体到不能再拆的一件事）。

【输入输出】
输入：（什么数据/什么操作进来）
输出：（要得到什么结果）
样例：（给一组真实的例子——输入长这样，输出应该长这样）
      ↑ 这一行最重要，给一个样例胜过描述十句

【约束】
- 技术限制：（版本、必须用什么、不能用什么）
- 规范要求：（命名、返回格式、错误码等团队规定）
- 安全要求：（哪些数据敏感、哪些操作不可逆）
- 不要做：（明确划出范围，防止它自作主张加功能）

【交付】
- 给我完整文件，从第一行到最后一行，不要用"其余省略"
- 多个文件的话逐个给，每个标清楚文件名和存放位置
- 最后单独说明：我要怎么验证这段是对的，做完应该看到什么
```

### 模板二：任务前的"选路"提问（不知道该用哪招时）

```
我现在要做的事情是：（用大白话描述你的处境，比如
"我接手了一个别人写的模块，要在里面加个功能，但我看不懂它"）。

请先不要给我代码，先帮我判断：

1. 这件事应该拆成几步做？按顺序列出来。
2. 每一步的目标是什么？做完应该达到什么状态才算过关？
3. 哪几步风险最高，做之前应该先备份或先确认什么？
4. 整件事里，有没有哪一步其实可以不做（我可能想复杂了）？

用大白话，我不是资深工程师。
等我确认这个计划之后，我们再一步一步开始。
```

### 模板三：结束前的自检（提交之前跑一遍）

```
下面是我这次要提交的代码，我需要你做一次严格的上线前检查。

【代码】
（粘贴完整文件）

【背景】
（这段代码是干什么的、会被谁调用、涉不涉及钱/权限/删除操作）

请按以下五关顺序检查，前三关最重要：

一、正：逻辑对不对？有没有算错、判断反了、漏了分支？
二、安：有没有安全问题？（用户输入没校验、权限没判断、敏感信息打进日志等）
三、错：可能失败的地方有没有处理？有没有空的 catch 把异常吞掉？
四、洁：命名清不清楚？有没有该拆的长函数、该删的重复代码？
五、快：有没有明显的性能问题？（尤其是循环里查数据库）

输出要求：
- 分成【必须改】【建议改】【可以不改】三档
- 每条都要说清楚：在第几行、会导致什么后果、怎么改
- 不要写"整体不错""写得很规范"这类废话
- 如果确实没有必须改的，直接说"没有必须改的"，不要硬凑
- 检查完，请再给我一个"会真出事的具体场景"，
  如果你想不出任何一个，就明确告诉我想不出来
```

## 下篇预告

**#93《提示词工程进阶：角色/模板/few-shot》**

你已经会"把话说清楚"了，但一定遇到过：

> **同样一个提示词，今天用效果炸裂，明天用一塌糊涂。**

下一篇解决**稳定性**问题：**角色**（为什么"你是一位资深工程师"有用）、**模板**（提示词变填空题）、**few-shot**（**给它 3 个例子它自己就学会了**）。
